# Change Request (CR‑002): Web App with UI — Final Specification (2025‑10‑06)

> Aligned with: **API Description Tool SRS v2**, **Solution Design**, and **CR‑001 Filtering**. Conversion logic and output schemas remain unchanged.

---

## 1) Background & Goals

The current CLI tool converts OpenAPI 3.x YAML files into three human‑readable tables (Parameters, Request Body, Response Body) and exports them as Excel or CSV. Distribution is limited because many BAs/POs prefer a browser‑based interface.

**Goals**

- Provide a minimal yet robust **web service** with a **simple UI** so non‑technical users can upload a spec, pick an endpoint, run conversion, and download results.

- Reuse the existing code path (parser → flattener → tables → writers) with **no changes** to conversion logic.

**Non‑Goals**

- No changes to conversion algorithms, column schemas, validation semantics, or filename derivation rules.

- No multi‑file or remote `$ref` resolution; no content negotiation expansion; no HTML portal doc export.

---

## 2) Users & Primary Flows

**Users**: BA/PO, QA, Backend dev (as readers).

**Core Flow**

1. **Upload** OpenAPI YAML (drag‑and‑drop or picker).

2. **Parse & Inspect**: app lists discovered `paths` and available HTTP `methods` per path.

3. **Select** **one** path and (when needed) **one** method.

4. Optional: toggle **OpenAPI validation** (default = **OFF**).

5. Choose **output format** (`xlsx` | `csv`, default = **xlsx**).

6. **Convert**. Show progress and real‑time log.

7. **Download** the output (workbook or zipped CSV set).

**Recovery Flow**

- If parsing/validation/filtering fails, show a clear error panel with suggested fixes.

---

## 3) Functional Requirements

**Upload & Status**

- **F001**: File input supports drag‑and‑drop and system picker; accept extensions `.yaml`, `.yml`.

- **F002**: Client‑side limit 10 MB; server hard limit 10 MB (configurable).

- **F003**: Show upload progress (percentage) and status (success/failure) with retry.

**Spec Inspection & Filtering**

- **F010**: After upload, server returns discovered `paths` and their `methods`.

- **F011**: UI enforces **exactly one** path selection; method selection is **required** if the path exposes multiple methods. Convert button remains disabled until valid input is set.

- **F012**: Validation toggle (`validate: on/off`) mirrors CLI/config behavior.

**Conversion**

- **F020**: Start conversion with payload `{path, method?, format, validate}`; server runs the **existing pipeline** unchanged.

- **F021**: Progress UI during conversion; render a live, scrollable **log** area (info/warn/error).

- **F022**: On success, display row counts per table and provide a **Download** button.

- **F023**: On failure, display an actionable error with hints (unknown path/method, OpenAPI validation errors, YAML load errors).

**Download**

- **F030**: `xlsx` → single file; `csv` → zipped archive containing `*_params.csv`, `*_req_body.csv`, `*_res_body.csv`.

- **F031**: Filenames follow the **existing precedence rule** (positional output → config → `<input_stem>_api_tab_desc`).

**Session & Retention**

- **F040**: Ephemeral storage; uploaded spec and generated artifacts auto‑deleted after **30 minutes** (TTL). TTL does not reset on download.

- **F041**: Janitor runs every **5 minutes**, logs cleanup actions (`JANITOR_DELETE upload_id=<id>`).

**Errors & Messaging**

- **F050**: Map common errors to friendly messages: multiple endpoints without method, method‑only specified, path not found, validation failure, YAML syntax error.

- **F051**: Each error mapped to stable HTTP status and code.

| Condition                 | HTTP | error_code                |
| ------------------------- | ---- | ------------------------- |
| Invalid YAML              | 400  | YAML_SYNTAX_ERROR         |
| OpenAPI validation failed | 422  | OPENAPI_VALIDATION_FAILED |
| Path/method missing       | 422  | PATH_OR_METHOD_NOT_FOUND  |
| File too large            | 413  | FILE_TOO_LARGE            |
| Wrong MIME/ext            | 415  | UNSUPPORTED_MEDIA_TYPE    |
| Job not found             | 404  | JOB_NOT_FOUND             |
| Too many jobs             | 429  | TOO_MANY_JOBS             |

## 4) System Design (MVP)

**Stack**

- **Backend**: Python **FastAPI** + Uvicorn.

- **Frontend**: Minimal SPA (React + Tailwind) or server‑rendered page.

- **Packaging**: Dockerfile for containerized deployment.

**Key Services**

- **Storage**: In‑container temp dir `/tmp/api‑desc‑uploads/{sessionId}` with TTL janitor.

- **Processing**: Call existing library entry points instead of shelling out. Keep modules `parser.py`, `flattener.py`, `tables.py`, `writer_*` untouched.

**API Endpoints (MVP)**

- `POST /api/upload` → returns `{upload_id, file_name, size, paths}`.

- `POST /api/convert` → runs conversion and returns `{job_id, status, rows, download_url}`.

- `GET /api/job/{job_id}` → `{status, logs, metrics, download_url?}`.

- `GET /api/download/{job_id}` → file stream.

- `DELETE /api/job/{job_id}` → cleanup.

**Examples**

- Upload request/response:

```json
{
  "upload_id": "uuid",
  "file_name": "booking.yaml",
  "size": 124523,
  "paths": {"/flights": ["get", "post"], "/hotels": ["get"]}
}
```

- Convert request:

```json
{"upload_id":"uuid","path":"/flights","method":"get","format":"xlsx","validate":true}
```

- Convert response:

```json
{"job_id":"uuid","status":"succeeded","rows":{"params":18,"request_body":4,"response_body":27},"download_url":"/api/download/uuid"}
```

- Error response:

```json
{"error_code":"PATH_OR_METHOD_NOT_FOUND","message":"'/foo' not in spec"}
```

**Concurrency and Limits**

- `MAX_CONCURRENT_JOBS=2`, `JOB_TIMEOUT_SEC=120`, `MAX_MEMORY_MB_PER_JOB=512`.

- When exceeded, server returns 429 `TOO_MANY_JOBS`.

**Security & Privacy**

- Allowed MIME types: `text/yaml`, `application/x-yaml`.

- Headers: CSP (`default-src 'self'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy` (restrict all by default).

- Disable directory listing for `/tmp/api-desc-uploads`.

- YAML loading: safe loader only.

- CORS disabled (internal network only).

## 5) Compatibility & Mapping

- **Conversion path** identical to CLI; no logic change.

- **Filtering semantics** follow CR‑001.

- **Validation** toggle aborts on validation failure when enabled.

- **Filename and sheet naming** remain as SRS.

- Outputs must be **byte‑for‑byte identical** to CLI for identical inputs.

---

## 6) UI & Accessibility

- Disable **Convert** until: file uploaded, path chosen, method chosen (if applicable).

- Show row counts (Params / Req Body / Res Body) after success.

- All controls accessible via keyboard; ARIA roles for progress/logs; visible focus indicators.

- Footer: `API Description Tool vX.Y.Z (abcdef0)`.

---

## 7) Observability & Versioning

- Emit structured logs with event markers (UPLOAD_START, PARSE_DONE, FILTER_APPLIED, CONVERT_DONE, ERROR_*).

- Metrics per job: `duration_ms`, `rows_{params,req,res}`, `validate_enabled`, `format`.

- Include `app_version` and `git_sha` in header and logs.

---

## 8) Non‑Functional Requirements

- **Performance**: Typical spec <2 MB completes ≤3 s.

- **Reliability**: Guard against recursive `$ref` cycles.

- **Portability**: Works in Docker (Windows/Linux).

- **Security**: As above.

- **Resource control**: Enforce limits for concurrency and memory.

---

## 9) Testing Strategy

**Unit**

- Upload validation, path/method extraction.

- Mapping (UI → internal filter rules).

**Integration**

- Upload → pick path/method → convert → download (seeded YAMLs).

- Validation on/off; unknown path/method; error mapping.

**E2E**

- Cypress/Playwright: drag‑drop, progress, logs, download.

**Regression**

- Ensure outputs byte‑for‑byte match CLI fixtures.

---

## 10) Rollout

- Phase 1: single‑node FastAPI + simple React UI; internal dockerized deployment.

- Phase 2: optional background jobs, auth (OIDC), persistent history, S3 storage.

---

## 11) Acceptance Criteria

1. User uploads YAML and sees accurate paths/methods.

2. Convert button active only after valid selections.

3. Default: `validate=false`, `format=xlsx`.

4. Conversion produces byte‑for‑byte identical Excel/CSV as CLI.

5. Validation toggle behaves per CLI/config.

6. Download works; filenames/sheets match SRS.

7. Errors return correct HTTP codes and friendly messages.

8. Per‑job metrics and logs visible; version displayed in UI.

9. TTL, janitor, and concurrency limits enforced and logged.

---

## 12) Implementation Environment

- **Auth**: none (internal use).

- **Retention**: 30‑minute TTL.

- **History**: single‑run UI.

- **Branding**: minimal Tailwind theme; configurable via env vars.

- **Hosting**: Docker container on shared VM.
